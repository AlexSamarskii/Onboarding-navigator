# G1a — стратегии уникализации Onboarding Navigator

**Автор:** Uniqueness Agent. **Статус:** proposal, требуется решение пользователя. Входы: `acceptance_criteria.yaml` (33 AC), `repo_map.json`, `baseline_report.md`, `uniqueness_input.json` из `.agent/artifacts/`. Версия основы — **0.14.6**.

Ниже предложены улучшения сверх утверждённых AC. Режимы, персональный план, чеклист, fallback, тикет, метрики, журнал вопросов и i18n readiness уже входят в scope и сами по себе не считаются уникализацией. Предлагаемые AC имеют временные ID **P-U01…P-U05**, не добавлены в acceptance criteria и не утверждены. «Покрываемые AC» означает связь с существующими требованиями, а не подтверждение их выполнения.

## Рекомендация MVP

1. **U01 — проверяемое основание ответа.** Оно усиливает доверие к ответам о льготах, доступах и политиках, используя те же утверждённые источники. Поддерживает **AC-S1, AC-S2, AC-S3, AC-S5, AC-S6, AC-F02, AC-C04, AC-C07**; новый результат проверяется отдельно по **P-U01**. Не требует доступа к корпоративным системам. Рекомендация условна доступностью достоверного происхождения контекста через внешний адаптер: подмена защищённого ядра ради цитирования запрещена.
2. **U02 — пошаговая IT-самодиагностика.** Добавляет практический путь решения двух конкретных проблем сверх ответа по FAQ; при этом сотрудник сохраняет возможность сразу попросить эскалацию. Поддерживает **AC-S1, AC-S6, AC-S7, AC-C04, AC-C05, AC-C07**; новый результат проверяется по **P-U02**. Узкий набор двух сценариев ограничивает объём редакторской проверки. Диагностические вопросы сами по себе не считаются RAG-fallback и не сбрасывают существующий счётчик.

U03 отложена до появления владельцев и дат пересмотра реального корпуса; U04 — до накопления достаточных обезличенных записей и решения включить AC-O02; U05 имеет меньший эффект, чем проверяемость и помощь в решении проблемы. Отсрочка U03/U04/U05 не снимает ни одного существующего mandatory AC.

## Предлагаемые AC для TZ Agent — не утверждены

| ID | Проверяемый результат / test hint |
|---|---|
| P-U01 | Для 12 контрольных пар AC-S1/S2/S3/S5 положительные integration fixtures предоставляют заведомо доступное происхождение, подтверждённое использованным контекстом. Во всех 12/12 ответах обязательны название разрешённого источника и дословная цитата из использованного фрагмента, соответствующая ключевому факту пары. Сообщение «основание недоступно» не засчитывается как успех положительного теста. Отдельные negative fixtures с неизвестным источником или отсутствием совпадения требуют RU-сообщение «основание недоступно» и отсутствие выдуманных ссылок; они не заменяют 12 положительных результатов. Правило AC-S6 сохраняется; защищённое ядро не изменяется, фактическая готовность точек подключения пока не проверена. |
| P-U02 | Для VPN и неполученного письма YAML описывает минимум две конечные ветви на сценарий, не более трёх уточняющих вопросов на путь; каждая конечная ветвь ссылается на утверждённый факт FAQ. На fixtures каждый путь приводит к ожидаемой инструкции или предложению эскалации. Бот не запрашивает пароли/токены и не запускает команды; явная эскалация доступна на любом шаге. Изменение развилки выполняется YAML без изменения кода. Счётчик AC-S7 меняется только по прежним RAG-событиям. Integration-тест всех путей. |
| P-U03 | До публикации локальная проверка предлагаемого YAML-реестра источников выявляет отсутствующего ответственного, неверную дату и истёкший срок пересмотра; вывод содержит список проблем и не публикует изменения автоматически. Корректный fixture проходит, по одному fixture каждого дефекта отклоняется; дата проверки фиксируется UTC. Индексация утверждённых источников AC-F02 и ядро RAG остаются прежними. Unit-тест с фиксированными часами. |
| P-U04 | При локальном запуске с частотой минимум 3 одинаковых нормализованных вопросов внутри mode/reason формируется Markdown-очередь групп с количеством, без исходных цитат, user_id и user_id_hash. Каждая группа получает непрозрачный локальный ID, не производный от текста вопроса или пользовательских данных, и номера строк разрешённого обезличенного исходного JSONL; ID однозначен внутри отчёта и позволяет отличить две группы с одинаковыми mode/reason/частотой. Редактор может сверить группу по этим номерам строк, новые персональные данные не собираются и записи автоматически не публикуются. Default-предложение: нормализация регистра и пробелов, без LLM-кластеризации; сортировка по убыванию количества и затем mode/reason/первому номеру строки. Fixtures с частотами 2 и 3, двумя режимами и двумя разными вопросами одной mode/reason проверяют порог, разделение, уникальность ID и точность ссылок на строки. Fixture с чувствительным значением подтверждает отсутствие этого значения и персональных идентификаторов в Markdown. При отсутствии входных записей отчёт явно пуст. |
| P-U05 | Для 12 контрольных пар AC-S1/S2/S3/S5 пользовательский выбор «кратко / подробно» меняет представление; в обоих вариантах сохраняются ключевые факты и условия AC-S6. Default-предложение: кратко — до трёх пунктов, подробно — полный утверждённый ответ; если ограничение мешает сохранить обязательные факты, приоритет у фактов. Выбор не меняет режим, язык или threshold. Integration fixtures двух форматов; смена профиля в YAML без изменения кода. |

## Проверка ограничений и фактическая база

- Все стратегии: **keep** multi-LLM fallback и RAG; **adapt** только YAML, контент и внешние локальные адаптеры. Rewrite не предлагается. Нет изменения `orchestrator/router.py`, `RAGChainFactory` или retrieval-ядра (**AC-C02/C03**).
- Сохраняются YAML-bundles и `modes.directory` (**AC-C04**). Новые YAML-метаданные, профили и развилки выше — **предложения**, а не найденные текущие config keys или реализованные hooks.
- Секреты остаются в разрешённом runtime-механизме по **AC-C05**, не появляются в YAML, цитатах, отчётах или prompts. Чтение секретных файлов для подготовки предложения не выполнялось.
- Нет календаря, голоса, EN, аналитического UI, HR-авторизации, изменения HR-данных или произвольных действий (**AC-C06**). UI-строки предполагаются только в RU-каталоге по **AC-C07**. Политики, FAQ и планы сохраняют Markdown-формат.
- Опоры из `repo_map.json`: `telegram_rag_bot/mode_loader.py` — bundles; `config_loader.py` — YAML; `handlers.py` — сообщения/режимы; `utils/session_manager.py` — сессии; `langchain_adapter/rag_chains.py` — защищённая RAG-фабрика. Пути здесь относительно `workspace/telegram-rag-bot/`; наличие конкретных точек подключения адаптеров не подтверждено и не предполагается как установленный факт. Архитектура и план файлов не строились.
- G0: wheel 0.14.6 подтверждён; **211 passed, 3 skipped**. Полный runtime **not_verified**, coverage **unknown**, Docker/K8s-артефакты целевой поставки отсутствуют. Поэтому оценки реализуемости — уровень стратегии; выполнение AC, latency и готовность deployment не заявляются.
- Примеры роли Uniqueness Agent с календарём и EN не использованы: явный scope пользователя и AC-C06 имеют приоритет. В AGENTS.md рядом с v0.14.6 осталась install-команда 0.10.0; для этого предложения принята подтверждённая в baseline **0.14.6**, файлы инструкций не менялись.
